## The loop

| # | Stage | Skill | Status | Reads | Writes |
|---|---|---|---|---|---|
| 0 | Interview | `gather-requirements` | New | A request to build something | Nothing; a confirmed read-back in the conversation |
| 1 | RFC | `create-rfc` | New | A problem, plus lessons marked for the next RFC | `docs/rfcs/<date>-<slug>.md` |
| 2 | Spec | `create-spec` | Exists | An approved RFC, or a conversation | `docs/specs/<date>-<slug>.md` |
| 3 | Tasks | `create-tasks` | Exists | A confirmed spec | `docs/specs/<date>-<slug>-slices.md` |
| 4 | Build | `implement-task` | Exists | One slice | Code and tests (uses `tdd`) |
| 5 | Review | `review-code` | Rename of `code-review` | The slice's diff and the spec | Findings |
| 6 | Test | `verify-work` | Exists | The built artifact | Verification report |
| 7 | PR | `prepare-pr` | Exists | The committed branch | Pull request |
| 8 | Release (optional) | `check-release` | New | The merged change | GO or NO-GO report with a rollback plan |
| 9 | Learn | `learn-lessons` | New | Every artifact above | `docs/lessons.md`, plus proposed changes |
| — | Driver | `deliver-feature` | Extend | The loop's state | Nothing of its own |

Stage 9 feeds stage 1. That edge is what makes this a loop.

## Decisions

1. **Names state each stage's purpose, verb first.** No shared prefix. _Why:_ user rejected the prefix scheme and proposed "naming them their stated purpose in the loop". (2026-11-11)
2. **`code-review` becomes `review-code`.** Breaking rename, recorded in `CHANGELOG.md`. _Why:_ user: "consistency matters to me, rename it". (2026-11-11)
3. **`check-release` is a gate, not a deployer.** It was first named `deploy-release`; the user asked what it does, and the name promised a deploy it never runs. The stage is optional: a library or personal tool can end the loop at the pull request. It checks readiness, requires a rollback plan, and returns GO or NO-GO. It runs no deploy command. _Why:_ user: "Gate only". (2026-11-11)
4. **`gather-requirements` interviews the user before anything is written.** When a user brings something to build, it walks through the request one question at a time until it holds everything a spec needs: who it is for, why, what done looks like, constraints, and what is out of scope. It ends with a read-back the user confirms, and writes no file. Its job is understanding the request, not attacking a plan. _Why:_ user: it "systematically walks through and questions the person in order to get all of the information required to create a spec and to have the model fully understand" the request. (2026-11-11)
4a. **The interview has one owner.** `create-rfc` and `create-spec` use the confirmed read-back and ask only about what it left open. `create-spec` keeps its own questioning for when it is called without a prior interview. _Why:_ `create-spec` already interviews; two skills asking the same questions would repeat them. (2026-11-11)
5. **An RFC settles which approach; a spec pins what gets built.** `create-rfc` records the problem, the options, a recommendation and open questions. `create-spec` accepts an approved RFC as input and stops re-asking what the RFC settled. (2026-11-11)
6a. **Review is one stage with four lenses.** `review-code` gains a Security lens beside Correctness, Spec, and Standards; it applies only when the diff touches a trust boundary. Design is reviewed earlier, on the RFC and the spec, where it is cheap to change. _Why:_ user asked for code, security, intent, and system design review; separate skills would produce overlapping reports. (2026-11-11)
6. **`review-code` joins the loop after every built slice.** Today it exists but nothing in the pipeline calls it. (2026-11-11)
7. **`learn-lessons` closes the loop.** It compares what was planned with what happened, writes each lesson with its evidence, and sends each lesson to its owner: project rules to `write-agent-instructions`, skill flaws to `create-skill` as a failing case, terms and architecture to the glossary or an ADR, product insight to the next `create-rfc`. `review-session` stays as the single-session tool and becomes one of its inputs. (2026-11-11)
8. **Two guards on learning.** A lesson needs a concrete event behind it, and a rule change needs the problem to have happened more than once. The skill also flags rules that never fired, so instructions can shrink. _Why:_ instructions that only grow degrade results. (2026-11-11)
9. **A judge decides whether a lesson is applied.** `learn-lessons` always writes the lesson, its evidence and the proposed change. A separate model, in a fresh context, then judges that change against fixed criteria: the evidence exists, the change follows from it, it contradicts no existing rule, and it is the smallest change that works. A pass applies the change as an uncommitted edit and records it in the ledger. Anything else stays a proposal. Changes to `learn-lessons` itself or to the judge's criteria are never auto-applied. _Why:_ user: "propose with evidence but apply if an llm as a judge passes it otherwise just propose". (2026-11-11)
10. **`deliver-feature` drives the whole loop.** It currently covers spec to verify. It keeps a human gate before the pull request and before release. (2026-11-11)

4. `check-release`.
