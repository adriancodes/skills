**Question 6 — Email delivery mechanism:** How should emails actually get sent — do you have (or want to sign up for) a transactional email provider like Postmark, SES, or Resend, or should we keep it provider-agnostic?

**Question 7 — Delivery timing:** Should sending an email block the user's action (assign/comment waits until the SMTP call finishes), happen asynchronously in-process (fire the action, send in the background of the same process), or go through a real job queue (Redis/BullMQ or similar)?

**My recommendation: asynchronous in-process, no queue infrastructure in v1.** Blocking the user action on an SMTP round-trip means a slow mail server makes commenting feel broken — that's a non-starter. A full job queue gives durability (emails survive a process crash) but drags in Redis and worker processes, which is heavy for an app this size. The middle path — write the notification event with a `pending` status, send it off the request path, mark it `sent`/`failed` — costs almost nothing and gives you an audit trail; and because decision 3 already made events first-class records, a crash loses at most the in-flight send, and upgrading to a real queue later is swapping the dispatcher, not redesigning the flow.
